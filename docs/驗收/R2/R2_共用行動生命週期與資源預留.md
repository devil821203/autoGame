## 範圍與設計

新增明確啟用的`Time.ActionRuntime`。共用ActionInstance保存委託人、工作者、活動種類／內容、起始與預計完成秒數、進度、AP實付總額、工作者體力實際消耗、版本及狀態歷史。AP欄位依原Charges重新核對，不是另一個AP帳戶；資產預留依原Ledger／escrow核對，不是另一個金錢／庫存餘額。

已接受的工作原子經過Proposed → Validated → Reserved → Running；對外快照只見已提交的Running／終態，歷史保留前述轉換。拒絕指令仍由既有Rejected事件記錄，不把失敗開始留下半份實例。

| 已轉接流程 | 已使用終態／進度 | 保留的原規則 |
| --- | --- | --- |
| 屬性／打坐／功法批次 | 每段Checkpoint，Completed／Interrupted | 起始付總AP、不退；每段才扣體力與給經驗；受襲／耗竭中斷，不重發已完成收益 |
| 自己進行醫療／製藥／鍛造 | Completed／Failed／Interrupted | 沿用原配方、品質亂數、起始成本、材料消耗與退款；不重寫產物公式 |
| 有償專職服務 | 同一Instance關聯Client／Provider、費用與材料預留 | 客供料只付手工費、師傅供料另含材料；成功才付款交貨，失敗／受襲全退費料，已付AP不退 |
| Demo／六角旅行 | Completed／Interrupted | 沿用原路線、逐格抵達、總成本；阻路中斷不新增退款規則 |

完工／失敗／中斷時釋放未用預留及容量，提升ActionVersion，使舊事件失效；結果解析器在副作用前檢查Running，不能以已完成實例再發成果。保留歷史與稽核資料，不自行裁剪。

Cancelled列入共用終態模型與終結處理；本輪沒有新增玩家主動取消修練的入口（既有規則不允許）。尚未把所有既有建造取消入口及一般排程工作接到此狀態機，不把列舉存在稱為全部取消玩法已完成。

## 預留與容量

ReservationService使用原escrow實際轉帳；同一預留ID同條件重試不再扣款，改條件重用ID拒絕。可部分消耗／部分返還，超額結算拒絕且不改餘額。Consumed對服務費表示已支付給工作者，不代表銷毀貨幣。客供材料仍保留原來的客戶→工作者→escrow／退回鏈，來源可從Ledger追溯。

有償服務費與生活原料已走共用Reserve／Settle。通用容量池須明確定義後才可預留，超額競爭只能一方成功，終結釋放。**正式世界沒有自動新增設施槽位上限**；目前容量1只出現在驗收fixture，符合原計畫「先用專項容量」範圍。未定設施規則／比例損失不啟用，也不另加為本批結案條件。

一致性檢查涵蓋AP來源角色、工作者／委託人與服務契約、工作進度、終態與活工作互斥、版本、狀態歷史、預留總額與權威帳本、容量超額及null快照。R2外部行動保留`service-work:`內部AP命名空間，避免與服務工作者記帳混用。

## 使用方式與設定

按Godot「R2行動／預留測試（重建）」建立新測試世界，原世界不被當成已遷移資料，原存檔保留。修練照原介面下令，狀態列顯示實例／預留數；凡人修為與人物屬性既有查詢頁顯示相關角色的R2工作內容、階段、段數、AP合計、工作者體力及版本。觀察NPC不取得控制權。

AP合計可能同時包含客戶與工作者各自實付，不代表從玩家一人扣兩次。預計DueAt不取代既有旅行／生活解析器的排程權威；本輪只改生命週期與資源入口。

本輪無新增平衡數值。成本／收益仍來自`config/time/action-costs.json`、`config/cultivation/mortal-actions.json`／`mortal-training.json`／`methods-proposal.json`、`config/life/recipes.json`／`service-prices.json`、`config/characters/stamina.json`及既有旅行設定。狀態列舉、格式版本、內部ID與單位換算屬工程結構，不是新的玩法參數。

三個原主要情境、R1入口與舊檔不自動啟用R2；R2世界開新局才保留R2模式。角色不能因此無視原行動Validator或任意動用其他角色／組織資產。
