# 既有專案漸進重構計畫（待批准）

日期：2026-10-29。依[差異分析](../分析/現有專案_規格差異分析.md)及新整合文件提出方案。**本次只交付方案，尚未開始任何下列程式重構，也未批准全部後續玩法。**

## 1. 修改原則與第一批建議

建議路線依序R0～R3（逐階段確認）：保護現況 → 統一時間事件 → 行動／資源政策 → 事件觸發AI。保留Godot畫面、既有計算器、帳本、配置、驗證與可用情境。R4～R7在核心穩定後分批批准；R8+是獨立玩法範圍，不阻擋前述重構完成。

不為對齊範例目錄而更名全部專案。保持現有`src/Domain`、`src/AI`、`src/Simulation`、`src/Persistence`、`src/Presentation`與`config/`；先建立有實際行為的接口／轉接器，沒有獨立部署或依賴需要時不拆空的Systems／Content類別庫。

新包P0～P7是新規格里程碑，不能覆蓋現有階段0～8。本計畫R編號專指整合工作：P0對應R0、P1對應R1、P3對應R2～R3、P5持久化對應R4、P4市場對應R5、P2真正多區生成／控制資格對應R6、P6壓測對應R7。因現有世界／角色骨架已存在，不再從空專案重做P2。

## 2. 建議目標結構

- `WorldTime`建議改為`long`整數分鐘，與引擎影格／物理步進無關；原10分鐘玩法定義不立即改值。若之後確需秒級事件，應在R0先選整數秒，不在同版存檔混用單位。
- `AdvanceTo(targetTime, maxEvents)`從統一最小堆按`(DueAt, SequenceId)`處理，事件執行時世界時鐘等於DueAt。遇阻斷事件返回停止時間／原因，不跳到原target。
- `ActionInstance`保存StartedAt、DueAt、State、Version、進度、預留參照及上下文。原Intent作為輸入，原各模組的Validator／結果計算器沿用。
- 完成、失敗、風險、通知只把相關Actor放入去重DecisionRequest；規劃器讀角色可知觀察，不能直接改世界。
- `Reservation`封裝現有資產帳本／escrow；不另造第二份可變金錢與材料餘額。AP、體力、服務費與材料可有不同消耗／退款policy。
- 存檔保存事件描述與資料，不序列化C#委派／Godot Node；載入後重建佇列與索引。先沿用全域SeededRandom以降低重播差異，獨立RNG streams屬之後可選改善。

以下檔名是預計修改／新增位置，尚未建立。所有新的玩法數值須依現有規範存config；本文選項不等於生效設定。

1. 目前World.SchemaVersion=3，已有1／2讀入處理。新時間／事件格式須新版本與清楚模式標識，不只靠某個可選欄位猜規則。
2. 有明確MinutesPerActionPoint的舊分鐘世界，可按保存的時間單位轉換Clock、到期、deadline、冷卻、觀察／記憶時間、忙碌時間、週期與重試；不是只改畫面時鐘。沒有權威時間單位的舊抽象Tick世界，先保留legacy或拒絕轉換，不能一律乘10。
3. 預留資產／已付AP／已消耗材料／剩餘批次必須原樣保留；不要透過再次TryStart「還原」活動，否則會重扣款。若某活動缺必要StartedAt／版本資訊，先確認可由收據重建，否則明確拒絕該進行中活動的轉換。
4. 重建佇列只產生尚未完成的事件；保存Processed／ActionVersion，不能同時從舊Work與新Event再加同一筆完成事件。
5. 使用者明確選擇轉換時另存新檔並提供前後不變量報告；不覆寫來源。獸皮ID舊檔不遷移、國家舊檔拒絕等既有例外不被本計畫取消。
6. 回退以最後舊版本快照為界，不承諾新資料無損降版；不可遇到轉換錯誤就清空人物／財產繼續載入。

## 5. 新／舊驗收的使用方式

- 原353項是既有功能基線，先跑實際數量，不硬湊通過數。新增DES事件／控制／訂單測試逐階段增加。
- 新引擎內同Seed／同輸入／同內容版本應可重現；跨引擎版本事件排序修正可能改變合法結果，須列出差異，不能只為保住舊Digest硬改順序。
- 原三套主情境仍分開驗收；每階段增加一個可玩的最小切片，不要求先完成世界全內容。
- 對未轉接活動保持舊模式隔離，不允許同世界一份資產被兩個引擎同時消耗。
- 每階段執行編譯、相關測試、Godot基本流程與存讀後才改狀態；壓測與長期經濟未跑就寫未驗證。
