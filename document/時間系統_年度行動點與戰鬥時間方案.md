# 時間系統：年度、每日行動點與獨立戰鬥方案

日期：2026-10-18。用途：依使用者時間需求整理方案；使用者已授權實作，新建「時間與AP測試」接線，舊存檔不遷移。不自動新增階段8。[實作及驗收](時間與AP系統_實作與驗收.md)記錄現況，以下歷史確認保留。

## 1. 已確認規則

| 項目 | 已確認內容 |
|---|---|
| 年度 | 1年120個世界回合 |
| 日期 | 1世界回合＝1日；預設第1年春季1日開始 |
| 季節 | 春、夏、秋、冬各30日 |
| 每日預算 | 每角色每日30行動點，實際行動次數依各行動成本決定；不是固定能做30次 |
| 行動成本與時間 | 各行動另存可設定的成本；每1行動點＝1個世界Tick |
| 推進 | 世界時間自動隨Tick推進，玩家與NPC同步；不等待玩家行動或結束本日按鈕 |
| 戰鬥成本 | 每場固定5點，可設定；發起者及主動加入的隊員各扣一次 |
| 戰敗／撤退 | 戰鬥開始後已扣的行動點不退 |
| 防守 | 被襲擊的防守方不扣戰鬥行動點，行動點不足也能自衛 |
| 玩家參戰 | 世界時間停止，戰鬥流程另算；戰鬥結束後補進5個世界Tick |
| NPC對NPC | 直接結算結果，不要求玩家逐輪觀看 |

例：若某行動成本1點，每日最多做30次；若成本3點，只做該行動則最多10次。全部預算只用在主動戰鬥時，最多6場；實際仍受生命、資格及其他行動支出限制。這些是預算示例，不是硬編AI必須做滿。

## 2. 分開三種時間，避免重用Tick

| 名稱 | 職責 | 是否推日期 |
|---|---|---|
| WorldDay／世界日 | 年、季、日、每日預算、日結事件 | 世界累計30Tick後自動日結加1 |
| WorldTick／日內模擬步 | 1AP＝1Tick，每日30Tick；角色活動共用時間軸 | 累計30Tick後進行日結換日 |
| CombatRound／戰鬥輪 | 先攻、移動、攻擊、戰鬥冷卻等 | 不加日期或日內步 |

畫面FPS、真實經過秒數及TickPump只是執行／播放頻率，不是第四種遊戲成本。手動暫停、玩家戰鬥暫停或關閉程式時不推世界時間；只是未下指令不再阻止Tick前進。

**與目前程式的差異：**現有`SimulationEngine.Step()`同時增加Clock.Tick、推世界、回復休息、處理事件及推進棋盤Round；不能只把Tick顯示改成日期就宣稱完成。新方案取代「每世界Tick一個戰鬥Round」的時間耦合，仍保留每戰鬥輪按先攻逐人移動後攻擊。

### 日期換算

以`DayIndex=0`代表第1年春季1日，保存絕對世界日索引，其他日期由核心計算：

```text
Year      = DayIndex / 120 + 1
Season    = (DayIndex % 120) / 30       // 0春、1夏、2秋、3冬
SeasonDay = DayIndex % 30 + 1
```

春30日結束後為夏1日；冬30日結束後為下一年春1日。首版不加入月份、閏日、季節災害或季節產量加成，季節只是已要求的日期結構。

## 3. 每日行動點與世界行動

### 建議的最小預算規則（待確認）

- 每日開始一次性回到30點，不累積未用點數、不透支；讀檔不重新補點。
- 先驗證資格、資源、時間、行動點，再原子接受行動。拒絕、重複提交、無效目標不扣點。
- 普通行動建議在合法開始時扣行動點；這與已確認的「執行完成後扣體力」是兩件事。體力仍按完成後扣除，不拿行動點代替體力。
- 場景查看、選目標、查看背包等介面操作不算世界行動；真正改變世界的操作必須明訂成本，不能用「轉帳／換物／取消」繞過預算。
- 建議可執行世界行動成本至少1；若要有0成本行動，須逐項列白名單並防止AI零成本循環。
- 玩家行動點用完後仍可看資訊、處理已開始的戰鬥及按結束本日；不強迫所有NPC一同停機。

### 行動設定建議

每項定義至少包含`ActionKind`、`ActionPointCost`、`WorldDuration`、付款時點及取消處理。行動點與世界工期已確認1:1：普通行動成本kAP就占用k個世界Tick。體力仍是獨立角色資源，不以AP代替。首版不另設可與成本矛盾的工期；舊長工期須明確換算。

| 行動 | 候選AP成本 | 注意事項 |
|---|---:|---|
| 買賣／兌換／任務交付 | 1 | 單次交易數量與批量上限仍需明訂，不能無限大量交易繞成本 |
| 採集／宗門採藥 | 2 | 只按真實執行收費，不因規劃候選或點選目標扣費 |
| 煉丹／宗門煉丹 | 3 | 原料、成敗與產物仍走既有帳本 |
| 修煉／學習 | 3 | 保留原丹藥／資金／時間與體力規則 |
| 休息 | 1 | 回復生命／體力的頻率需重新定義，見第7節 |
| 旅行 | 待定 | 按整段或每格計費需選一種，不與既有整段體力成本混淆 |
| 主動戰鬥 | **5，已確認** | 每名主動參戰者每場一次，不按戰鬥輪重複扣 |

除戰鬥5點外，以上AP值均為候選，不是正式已確認平衡設定。建造、政策、招募、邀請與開箱等既有指令也要列入成本表，不能只替生產加限制。

## 4. 世界自動推進與多Tick行動（最新確認）

世界時間自行隨Tick前進，不由玩家提交行動才推進。每天30Tick，滿30Tick自動日結／換日。這取代先前「玩家行動才推進、按結束本日補時間」流程；首版不再要求結束本日按鈕。暫停及玩家戰鬥仍是已確認的例外。

**佔用多Tick＝持續執行同一行動，不可開始新行動。** 不是取消原行動，也不是每個Tick重新採集一次；獎勵只在完成所需Tick後、該Tick結束時結算一次。

### 採藥佔2Tick的例子

| 時間 | 玩家狀態 | 是否可新選行動 | 產出 |
|---|---|---|---|
| 第1Tick開始 | 選擇採藥，進入忙碌，需2Tick | 本Tick已開始一次，不再接新行動 | 無 |
| 第1Tick結束 | 已完成1／2Tick | 仍忙碌 | 無 |
| 第2Tick開始 | 繼續原採藥，不做新決策 | 否 | 無 |
| 第2Tick結束 | 已完成2／2Tick，結算後解除忙碌 | 本Tick不追加新行動 | 按既有採藥規則結算一次 |
| 第3Tick開始 | 空閒 | 是 | 新行動另算 |

以上是排程示例，不修改既有採藥產量／成功機率／歸屬。普通採集歸個人，宗門工作仍歸宗門；材料消耗與失敗規則沿原行動定義。

### 每Tick建議固定順序

1. 讀取Tick開始時角色狀態；僅空閒、有資格且有足夠AP者可選擇／接受一個新行動。
2. 忙碌者延續既有行動，不再次規劃、扣同一份成本或建立新任務。
3. 統一推進所有角色當前行動的進度一個Tick。
4. Tick結束時結算已完成工作：實際原料／產出／收益、已確認的完成後體力消耗、任務收據與事件。
5. 解除已完成行動的忙碌，但新行動最早在下一Tick開始；再判定30Tick的日結及換日。

1Tick行動也是開始該Tick、結束該Tick結算，不額外等待第2Tick。推薦以「開始前的時間邊界＋耗時」保存完成邊界：邊界0開始耗時2的行動，邊界2完成，避免把第1Tick開始記為1後又加2，誤變第3Tick才完成。

所有角色共用同一時間軸：30名NPC同時採藥2Tick，世界只經過2Tick，不是60Tick。每角色同時最多一項行動，不能趁忙碌逐Tick發起轉帳／採集或在完成當Tick再補一次行動。

玩家未輸入時可保持空閒，世界照常推進；空閒不等於休息，不自動給採集獎勵或回血。NPC依既有自主策略在空閒時決策；執行中只追蹤進度，避免每Tick重新搜尋計畫。休息作為明確的持續行動，其回血／體力回復時點需接入同一Tick結束流程，不把一般工作或無指令誤當休息。

每日仍30AP、1AP＝1Tick；沒有動作的Tick也會經過。AP的正式扣除時點（起手保留／完成結算）仍待定案，但同一2Tick行動不能起手扣2後、兩個忙碌Tick再各扣一次。剩餘AP不足時不能開始付費新行動，已合法開始的工作仍需按已確認的跨日／中斷規則處理，不因未收到下一個玩家指令而停住世界。

建議保存絕對WorldTick及工作StartedBoundary／DueBoundary，日期依每30Tick推導；另存必要的日結收據與角色預算所屬日，避免重載存檔重補AP或重領獎勵。從世界Tick0開始，第1～30Tick屬春1日，第30Tick結束完成日結，第31Tick開始屬春2日。

跨日工作（例如第30Tick開始採藥、次日第1Tick結束完成）、角色被襲擊造成的工作中斷、工作途中取消及AP歸屬日，仍須明確定案；不能用改日期或重設預算的方式清除工作／重扣原料。分幀處理與FPS只影響現實等待，不改應執行的Tick數。
### 玩家自主排程與優先級

使用者追加：玩家角色在未手動控制時也能自主選行動；玩家可設定行動優先級的操作介面先列「待確認及後續擴充」，測試Demo先實作自動排程。正式排序項目／絕對次序或權重／中斷與保存仍待確認，不直接套用新規則。

Demo已用現有Tick引擎接既有Utility AI：玩家空閒才排程、有手動Pending時不自動排、工作忙碌時不接新動作；此Demo不代表新日曆與AP系統已完成。詳見[玩家自動排程Demo驗收](玩家自動排程Demo_實作與驗收.md)。新時間核心實作後再把同一決策入口接到每Tick開始的空閒階段。

## 5. 戰鬥成本與中斷規則

### 固定5點如何扣

以唯一BattleId及角色ID產生一次成本收據，避免開關畫面、讀檔、重複指令或自動戰鬥重扣。

- 發起者與同意主動參戰的隊員各需5點，戰鬥正式成立時扣一次。
- 有人缺點數時如何處理主動組隊，建議先排除不能負擔的主動隊員並重新徵求組隊／出發資格，不替其透支或強制參戰；具體策略仍待確認。
- 防守者不扣，包括玩家被襲擊。主動／防守由觸發來源認定，不能以誰先攻擊、速度較快或誰贏來認定。
- 戰鬥正式成立前驗證失敗不扣；成立後撤退或戰敗不退，勝利也不退。
- 普攻／移動不再每輪扣5世界AP；技能若耗MP、物品或其他戰鬥資源，另外依定義結算，不暗中新增戰鬥內AP制度。

副本／探索遭遇是重要缺口：若探索本身另耗AP，剩餘預算不足5時不能先抽到怪再假裝沒遇見。建議對「主動冒險可能觸發戰鬥」先保留5點；沒有戰鬥則釋放保留，有戰鬥才收取。一般旅行被襲擊則按防守規則。探索是否另收一次普通行動成本，仍需確認，防止同一戰鬥多收或逃避成本。

### 玩家參戰：世界暫停

在一個完整世界步的提交邊界建立戰鬥，不在交易提交一半時停住；把「下一世界步」凍結。所有世界角色的旅行、製作、俸祿、任務期限、恢復及日期均停止；不是只停玩家身邊。

另呼叫`AdvanceCombatRound()`推戰鬥，不能呼叫會加世界時間的`StepWorld()`。玩家手動與自動戰鬥都如此；自動戰鬥只自動出戰鬥指令，不恢復世界時間。

已確認採「戰中凍結，戰鬥結束後補進5個世界Tick」。這5Tick需依序處理正常NPC、工作與週期事件，不是只把時鐘數字加5；對玩家呈現為一次戰後時間結算。打20個戰鬥Round仍只補5個世界Tick。多人主動參戰各扣5AP，但同一場共同時間只推5Tick，不依人數重複加時；防守者不扣AP，也仍承受這場戰鬥經過的世界時間。

建議戰後處死／必要結算及玩家死亡選角期間仍凍結，結算完成後才恢復世界；這段額外凍結尚待確認。已領取的普通寶箱日後開啟是否耗世界AP另列成本，不強制把所有開箱都延長戰鬥暫停。

若同一世界步產生多場與玩家相關的請求，以事件序號處理並鎖住參戰者，不允許同一角色同時加入兩場或重複付費。

### NPC對NPC：直接結果

建議使用**同一套戰鬥核心與AI**在不播放畫面的情況下跑到終局，再一次提交結果；不是另寫只比較總戰力、忽略傷亡與資源的必勝公式。

每場仍保留個體傷害、失能／死亡、技能與消耗、掉落來源、戰鬥AP成本、亂數狀態與收據。戰鬥輪數不推日期，也不在內部迴圈觸發世界休息或薪資。若採5AP＝5Tick，NPC參戰者在共同時間軸占用5Tick，不能每處理一場NPC戰鬥就讓全世界另加5Tick；直接算出的結果要在開始或完成時發布，仍需一併定案，避免NPC於5Tick內反覆即時開戰。

NPC需要看得見的對手資訊，不能為了直接結算而讓決策讀取敵方完整背包。最大輪數、平局及控制權規則與玩家戰鬥一致。計算成本過高時可分批或事件佇列處理，但不能以效能理由偷偷改結果規則。先量測再決定是否另需近似模式。

## 6. 資料與模組建議

| 資料／介面 | 職責 |
|---|---|
| WorldCalendar／DayIndex | 唯一日期來源；不重複保存可相互矛盾的年季日 |
| DailyActionBudget | ActorId、BudgetDay、RemainingAP、已扣成本收據 |
| ActionCostDefinition | 行動AP及對應Tick（1:1）、退款／中斷規則 |
| WorldDayPhase | 世界運作、Tick結束結算、日結、玩家戰鬥暫停等持久階段 |
| WorldScheduler | 旅行／工作／事件及NPC的日內順序，不受動畫速度影響 |
| AdvanceWorldTick／CommitTickEnd | 世界Tick及完成／日結的受控入口，不依賴結束本日按鈕 |
| AdvanceCombatRound | 只推戰鬥，不動世界日期與世界排程 |
| ResolveNpcBattle | 共用核心的無畫面迴圈，限次且保留亂數與個體結果 |
| TimeRules／ActionCosts | 新建世界讀分類設定，運行世界及存檔保留規則快照 |

建議設定位置：`config/time/calendar.json`、`daily-budget.json`、`action-costs.json`、`combat-time.json`。本次不建立未定數值的正式JSON，也不把原Tick欄位無差別更名。

AP不是可交易物品，不放進靈石庫存；但每筆扣除、重設與戰鬥成本需有可稽核的行動收據。一次世界行動要一起驗證AP、體力、背包、資金、占格／位置及排程，不能分開成功一半。

## 7. 舊功能的時間單位必須逐項決定

| 功能 | 現況 | 新方案需決定 |
|---|---|---|
| 旅行／採集／煉丹／修煉／學習／建造 | 多以Tick排程 | 工期按1AP＝1Tick換算；超過本日剩餘時間如何拆段／跨日 |
| 休息 | 現為每Tick體力15／30／45、昏厥10，生命10 | 回復改為每次休息或每日？一次休息占多少日內時間？不能把舊每Tick直接當每整日，或免費無限回復 |
| 俸祿 | 現行檔案每10Tick、每人10靈石；早期需求曾為30 | 新週期以日計還是日內步，金額是否保持，需獨立確認，不趁時間改版自行恢復30 |
| 收購／任務發布／考核 | 目前20／20／120等Tick設定 | 新世界各隔幾日、預算／收入頻率與任務到期如何換算 |
| AI記憶／計畫期限／LOD | Tick與決策預算 | 記憶衰減按日或日內步；不能戰鬥20輪就忘掉世界情報 |
| 冷卻／傷勢／技能 | 世界與戰鬥口徑未完全分開 | 每效果標明WorldDay／WorldStep／CombatRound，戰鬥凍結世界效果 |
| 聚落人口／季節 | 部分尚未實作 | 日期先做，不擅加季節產銷、人口加成或新事件 |

長時間工作的候選規則：保留已有原料與完成度，分工作段消耗當日AP，不因次日預算重設就重扣全部原料；無法負擔下一段時停工到可合法續作。與原「行動完成後扣體力」如何銜接仍需定案，避免每段及全程重複扣體力。

## 8. 存檔及舊模式

建議先新增時間模式版本，**新建時間測試情境啟用，舊檔維持舊Tick模式**。過去的181項及現有雙陣地紀錄仍是舊時間模式證據，不直接當作新系統驗收。

不能將舊Tick400直接說成第4年夏11日，也不能把原4Tick工作無說明改成4日。若日後要遷移，需明列原單位、剩餘工期、任務期限、日結收據與世界日期映射，先保留原檔再轉換。

保存日期、日結階段、各角色剩餘AP／所屬日期、成本收據、工作剩餘量、戰鬥暫停來源、戰鬥Round／待提交指令／亂數。讀取途中玩家戰鬥時世界仍凍結，不重新收5點、不重設每日30點。沿用已確認「關閉後不進行離線推進」。

## 9. 建議開發順序與驗收
